# CocosMCP 测试页面功能 - 可行性分析

## 1. 需求概述

在 Cocos MCP Server 插件面板中新增"打开测试页面"按钮，点击后在浏览器中打开一个 HTML 测试页面，
可以在该页面上可视化地测试所有 MCP 工具接口（场景操作、节点操作、组件操作等 50 个工具）。

## 2. 参考项目分析：Unity Ember Skill Tester

### 2.1 架构总览

Unity 项目 `E:\UnityProjects\UnityCli\UnityPackage` 已实现了完整的测试页面系统，其架构如下：

```
[Unity Editor Window]     EmberWindow.cs（用户点击"打开技能测试页"按钮）
        |
        v
[HTTP Server Layer]       UnityHttpListener.cs（后台线程接收HTTP请求, 主线程处理）
        |
        v
[Route Controller]        EmberRegistryController.cs（路由分发 + Skill执行）
        |
        v
[Tool Discovery]          EmberToolDiscoverer.cs（反射扫描 [EmberSkill] 标记的方法）
        |
        v
[Skill Definitions]       Editor/Extensions/Skills/*.cs（被 [EmberSkill] 标记的静态方法）
        |
        v
[HTML Test Page]          skill-tester.html（前端页面，通过 /tools 和 /skill/{name} 通信）
```

### 2.2 关键实现细节

#### 入口：EmberWindow.cs

用户在编辑器窗口点击"打开技能测试页"按钮，调用 `Application.OpenURL` 在浏览器打开
`http://localhost:{port}/skill-tester`。

#### HTTP 路由表

| HTTP 方法 | 路径 | 功能 |
|-----------|------|------|
| GET | `/skill-tester` | 返回 HTML 测试页面 |
| GET | `/tools` | 返回所有技能列表（按分类分组的 JSON） |
| POST | `/skill/{name}` | 执行指定名称的技能 |
| OPTIONS | `*` | CORS 预检响应 |

#### 前端页面（skill-tester.html，808 行，自包含单文件）

功能特性：
- 按分类 Tab 切换显示技能列表
- 参数表单 / JSON 编辑器双模式切换
- 参数类型自动转换（number/boolean/array/object）
- 参数值记忆（localStorage 持久化）
- 执行历史记录（最多 20 条，localStorage 持久化）
- Copy as cURL 命令
- JSON 语法高亮显示
- 请求/响应详情弹窗
- 搜索过滤技能

#### 资源加载：SkillTesterAssets.cs

从文件系统读取 `skill-tester.html` 内容，带有缓存机制。路径定位采用三种策略：
MonoScript、StackTrace、硬编码路径。

#### 线程模型

Unity 采用严格的生产者-消费者模式：
- HTTP 线程（生产者）：后台线程接收请求，仅做解析和入队，绝不调用 Unity API
- 主线程（消费者）：通过 `EditorApplication.update` 每帧从队列取请求处理

## 3. CocosMCP 现有架构分析

### 3.1 HTTP 服务器现状

CocosMCP 已有一个完整的 HTTP 服务器（`source/mcp-server.ts`），基于 Node.js 原生 `http` 模块：

```
MCPServer
  ├─ http.createServer() + listen(127.0.0.1:port)
  ├─ handleHttpRequest(req, res)  路由分发
  │     ├─ POST /mcp               MCP 协议端点（JSON-RPC）
  │     ├─ GET  /health            健康检查
  │     ├─ POST /api/{cat}/{tool}  简化 API（已有！）
  │     └─ GET  /api/tools         工具列表（已有！）
  ├─ setupTools()                  装配 50 个工具
  └─ executeToolCall(name, args)   执行工具
```

### 3.2 现有路由与 Unity 的对比

| 功能 | Unity 实现 | CocosMCP 现状 | 差异 |
|------|-----------|--------------|------|
| 返回 HTML 页面 | `GET /skill-tester` | 无 | 需新增 |
| 工具列表 | `GET /tools`（按 categories 分组） | `GET /api/tools`（扁平数组） | 格式不同，需适配 |
| 执行工具 | `POST /skill/{name}` | `POST /api/{category}/{toolName}` | 路径不同，需适配 |
| CORS | 有 | 有（已设 `Access-Control-Allow-Origin: *`） | 无需改 |
| 打开浏览器 | `Application.OpenURL` | `shell.openExternal`（已有 openExternalUrl 方法） | 无需改 |

### 3.3 关键优势：CocosMCP 已有 90% 基础设施

| 能力 | 现状 | 说明 |
|------|------|------|
| HTTP 服务器 | 已有 | `http.createServer()` 绑定 127.0.0.1:port |
| 工具列表 API | 已有 | `GET /api/tools` 返回 `{ name, category, toolName, description, apiPath, curlExample }` |
| 工具执行 API | 已有 | `POST /api/{category}/{toolName}` 执行工具并返回结果 |
| 工具 Schema | 已有 | 每个 `ToolDefinition` 包含 `inputSchema`（JSON Schema 格式） |
| CORS 跨域 | 已有 | 已设置 `Access-Control-Allow-Origin: *` |
| 打开浏览器 | 已有 | `openExternalUrl(url)` 方法通过 `shell.openExternal` 打开 |
| 静态文件目录 | 已有 | `static/` 目录存放插件静态资源 |

### 3.4 线程模型对比

| 维度 | Unity (C#) | CocosMCP (Node.js) |
|------|-----------|-------------------|
| 线程限制 | Unity API 必须主线程调用，需生产者-消费者队列 | Node.js 单线程，无此限制 |
| HTTP 处理 | 后台线程接收 → 主线程处理 → 回后台发送 | 直接在事件循环中处理 |
| 复杂度 | 高（ManualResetEventSlim + 队列） | 低（直接 async/await） |

CocosMCP 是 Node.js 环境，HTTP 请求处理本身就是异步非阻塞的，不需要 Unity 那套
生产者-消费者队列，实现更简单。

## 4. 可行性结论：完全可行，改动量小

### 4.1 需要新增的部分

```
改动清单：
  1. [新增] static/skill-tester.html          测试页面 HTML（参考 Unity 版本适配 CocosMCP API）
  2. [改动] mcp-server.ts handleHttpRequest    新增 GET /skill-tester 路由，返回 HTML
  3. [改动] mcp-server.ts                      新增 /tester/tools 和 /tester/execute 路由（适配前端期望格式）
  4. [改动] panels/default/index.ts            面板新增"打开测试页面"按钮
  5. [改动] main.ts                            注册 open-tester 消息处理
```

### 4.2 不需要改动的部分

- HTTP 服务器创建、监听逻辑 — 已有
- 工具注册、执行逻辑 — 已有
- CORS 跨域处理 — 已有
- 打开浏览器方法 — 已有
- 工具 Schema 定义 — 已有

### 4.3 API 适配方案

Unity 前端期望的 API 格式与 CocosMCP 现有格式略有不同，有两种适配策略：

**方案 A（推荐）：新增测试页面专用路由，不改现有 API**

```
GET  /skill-tester              返回 HTML 页面
GET  /skill-tester/api/tools    返回按分类分组的工具列表（适配前端 categories 格式）
POST /skill-tester/api/execute  统一执行入口（body: { tool, arguments }）
```

优点：
- 不影响现有 /api/tools 和 /api/{cat}/{tool} 接口
- 前端 HTML 可以直接复用 Unity 版本的 fetch 逻辑（只需改路径）
- 分类分组格式更友好

**方案 B：前端适配现有 API**

前端 HTML 中的 fetch 路径改为 CocosMCP 现有的 `/api/tools` 和 `/api/{category}/{toolName}`。
需要在前端 JS 中做格式转换（扁平数组 → categories 分组）。

优点：后端零改动（除新增 HTML 路由外）
缺点：前端逻辑稍复杂

## 5. 实施计划

### 阶段 1：最小可用版本（MVP）

1. 创建 `static/skill-tester.html`，基于 Unity 版本适配 CocosMCP 的工具格式
2. 在 `mcp-server.ts` 的 `handleHttpRequest` 中新增 `GET /skill-tester` 路由返回 HTML
3. 新增 `GET /skill-tester/api/tools` 路由，返回按分类分组的工具列表
4. 新增 `POST /skill-tester/api/execute` 路由，统一工具执行入口
5. 在面板 UI 新增"打开测试页面"按钮

### 阶段 2：体验优化（可选）

## 6. 风险评估

| 风险 | 等级 | 说明 |
|------|------|------|
| 影响现有 MCP 协议 | 低 | 新增路由独立于 /mcp 端点，不影响 JSON-RPC |
| 影响现有 /api/* 接口 | 低 | 方案 A 新增专用路由，不改现有接口 |
| HTML 文件找不到 | 低 | 编译后 __dirname 为 dist/，回溯 static/ 即可，已有 icon.png 同理 |
| 端口未启动时点击 | 低 | 按钮仅在 server running 时可用（参考 Unity 按钮逻辑） |
| 安全性 | 低 | 绑定 127.0.0.1，仅本机可访问 |

## 7. 类比理解

可以把这个功能理解为给 MCP 服务器加了一个"自带的使用说明书 + 遥控器"：

- 现在的 CocosMCP 就像一个只有 API 文档的后端服务，你必须用 Claude CLI 或 Cursor 等
  AI 客户端才能调用它的接口
- 加了测试页面后，就像 Swagger UI / Postman 一样，任何开发者打开浏览器就能：
  - 看到所有可用工具的列表和参数说明
  - 填写参数表单或直接编辑 JSON
  - 一键执行并查看返回结果
  - 查看执行历史
- 这对于开发调试、验证工具是否正常工作、向新用户演示功能都非常实用
